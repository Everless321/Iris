# raw_tunnel relay 改 io::copy + try_join — 多跳 zero-alloc 流式转发

## 改动
`crates/node/src/raw_tunnel.rs::relay()` — 中转节点的逐帧 read_frame/write_frame loop × 2 task 改为：
```rust
let _ = tokio::try_join!(
    tokio::io::copy(&mut r, &mut nw),
    tokio::io::copy(&mut nr, &mut w),
);
```

net diff: -25 / +7 (净 -18 行)

## 设计理由
中转节点根本不需要解析 frame 边界 — 入口 (handle_entry_tcp) 包 frame、出口 (exit_tcp) 拆 frame，relay 只是字节流透传。
原实现每帧 `vec![0u8; len]` 堆分配 + 4 次 syscall (length/body × 2) + 2 个 tokio task 是冗余的。

mTLS 加解密不变 — 每个 hop 间仍是独立 TLS 终结 (中转节点解密 → 重加密)。
本次优化只剥掉「frame 解析层」，安全模型不变。

## 实测数据 (GCP n2-standard-4 us-central1-a, RTT 0.3ms)

### TCP P1 (单流) - 中位数

| 跳数 | ring | aws-lc-rs | **copy_bidir** | 备注 |
|------|------|-----------|----------------|------|
| 1-hop | 6.88 | 9.50 | 7.38 (range 6.5-8.9) | 不走 raw_tunnel，单跳抖动来自 GCP 邻居 |
| 2-hop | 3.48 | 3.55 | 3.32 | 单流瓶颈仍在 TLS 加解密 (CPU bound) |
| 3-hop | 2.84 | 3.07 | 3.23 | 同上 |

### TCP P8 (多流，业务真实场景) ⭐

| 跳数 | ring | **copy_bidir** | 提升 |
|------|------|---------------|------|
| 1-hop | 9.47 | 9.61 | +1.5% |
| **2-hop** | 5.81 | **6.46** | **+11%** |
| **3-hop** | 3.75 | **🚀 5.40** | **+44%** |

## 关键观察
- **P1 单流多跳几乎持平** — 单流 CPU bound 卡在 TLS 加解密，io::copy 加速的 framing 层占比小
- **P8 多流多跳大幅提升** — framing 开销在多流下被显著摊薄，zero-alloc 优势体现
- **真实业务多为多流** (HTTP/2 连接池、ss 多客户端、CDN 回源等)，实际收益对齐 P8 数据
- **0 回归** — 单跳和多流 1-hop 都微涨或持平
